# Legacy Site Audit Plan v0.1

状态：当前有效 / 待执行  
创建目的：在重新开发新版个人网站前，系统审计旧网站的页面结构、内容、功能、证据和问题，并将结果映射到新的 Working Archive 架构。

---

## 0. 本计划要回答什么

旧网站已经可以运行，但它不是新版的视觉和内容权威。

本次审计要回答：

1. 旧网站现在实际有什么页面、区块、内容和交互；
2. 哪些内容仍然准确，哪些内容已经过时或不能代表 Maki；
3. 哪些页面职责重叠，尤其是 Projects 和 Works 如何合并到 Archive；
4. 哪些内容适合进入新版 Home、Archive、Now、About、Contact；
5. 哪些内容需要补充证据、重写、降级或删除；
6. 旧网站中哪些表现会把新版带回明显的 AI 味；
7. 在不复制旧网站结构的情况下，如何安全地迁移真实内容。

本计划不负责：

- 直接重写页面；
- 直接修改生产代码；
- 现在写完全部最终文案；
- 重新选择视觉方向；
- 为旧页面寻找新的装饰组件。

## 1. 当前已经确定的新版约束

### 1.1 网站目标

网站要成为一个长期存在、持续更新的个人工作档案。访客应该能够看到 Maki 当前在做什么，也能逐渐了解做过的工作和留下的证据。

问卷中“访客首先应该记住什么”的答案是：

> 我会持续在网站更新。

这说明持续更新是重要的站点承诺，但它暂时还不是一句完整的个人定位。这个差异记录为开放问题，不阻塞本次审计。

### 1.2 Home

当前暂定为：

1. Hero / 身份介绍；
2. Live Index / 当前身份、地区、方向、开放机会；
3. Current Workbench / 当前正在做的事情；
4. Selected Work / 代表性工作；
5. Contact / 联系入口。

Home 不单独加入 Current Questions、Open Loops、Currently Reading 或 Archive 入口区块。更新内容由 Archive 和 Now 承担。

### 1.3 Archive

Projects 和 Works 统一为 Archive。

第一版候选条目：

- Maki English 自媒体，已归档；
- 英语教育产品与社群交付，已归档；
- AutoCoder 实习经历，已归档；
- AdventureX 黑客松，已归档。

暂不进入第一版：

- Audibooker；
- 个人网站重建；
- 知识系统或其他系统。

上述“暂不进入”是第一版范围决定，不代表这些内容永远不公开。

### 1.4 第一个详情页

第一详情页候选为：

> 英语教育产品与社群交付。

详情页最重要的内容：

1. 最终结果；
2. Maki 的具体角色；
3. 证据和验证。

同时保留 AI 参与边界。截图、平台数据截图、代码或仓库是当前愿意公开的证据形式。

### 1.5 Now

Now 记录：

- 2–4 个当前重点；
- 为什么现在做；
- 当前问题；
- 正在读或学习的内容。

Now 在明显阶段变化时更新，并显示真实的最后更新时间。

### 1.6 About 和 Contact

About 暂定为短页面，重点是：

- 背景；
- 职业方向；
- 长期兴趣；
- 几个关键转变。

Contact 的优先级：

1. 项目合作；
2. 求职；
3. 普通交流。

当前首选渠道是微信。审计时要确认邮箱是否作为并列或备用入口保留，以避免只依赖二维码造成联系阻力。

## 2. 审计原则

### 2.1 旧网站是证据，不是设计参考

审计旧网站时会把以下内容分开：

- 内容事实：可能迁移；
- 页面结构：需要重新判断；
- 功能交互：评估是否值得保留；
- 视觉表现：只记录问题，不默认继承；
- AI 味和模板化表达：作为负面证据记录。

旧网站中的颜色、字体、卡片、动效和文案不会因为已经存在，就自动进入新版。

### 2.2 先观察，再评价

每个结论都尽量区分证据等级：

- CODE：从源码或数据文件确认；
- STATIC：从静态构建结果确认；
- RUNTIME：在本地运行页面中观察到；
- INTERACTION：实际点击、hover、展开或弹窗确认；
- USER：需要 Maki 判断或确认；
- INFERENCE：根据以上证据提出的推断。

没有运行时证据时，不把源码中的意图写成已实现功能。

### 2.3 不要求一次性解决全部不确定性

以下内容可以在审计中继续保持开放：

- Home Hero 的最终个人定位；
- 项目共同主线的最终说法；
- 旧内容的删除和降级；
- 每个条目的完整证据；
- Future 页面；
- 最终文案。

开放问题必须被记录，而不是被默认为已决定。

## 3. 审计阶段和工作流

## 阶段 A：建立旧网站证据包

### A-1. 页面和代码清点

清点：

- 页面路由；
- 页面入口；
- 页面之间的链接；
- 组件；
- 内容数据；
- 图片和其他静态资源；
- 第三方依赖；
- 旧项目和作品的分类方式。

当前优先检查：

- Home；
- Projects；
- Works；
- About；
- Contact。

### A-2. 运行时观察

在本地运行旧网站后，对每个页面记录：

- 首屏；
- 每次滚动后的区块；
- 页面长度；
- 桌面端布局；
- 移动端布局；
- 空状态；
- 加载或错误状态；
- 页面内部和外部链接。

### A-3. 交互检查

逐项检查：

- Header 导航；
- CTA 按钮；
- 项目和作品卡片；
- 外部链接；
- details 或折叠内容；
- 二维码和弹窗；
- hover；
- focus；
- 键盘可达性；
- 返回路径；
- 主题切换，如果旧版存在；
- 移动端触摸操作。

只记录确实观察到的行为，不从组件名称推测行为。

### A-4. 截图和命名

建议保存：

- 每个页面的桌面端完整截图；
- 每个页面的移动端完整截图；
- 每个重要交互状态的截图；
- 旧首页每个主要滚动区段的截图；
- 关键问题的局部截图。

截图需要能追溯到：

- 页面；
- 视口；
- 滚动位置或交互状态；
- 截图时间。

原始截图属于审计证据，不直接作为新版网站资源。

## 阶段 B：内容和结构审计

对旧网站的每一个内容区块填写审计矩阵。

| 字段 | 要记录什么 |
| --- | --- |
| Audit ID | 唯一编号，例如 HOME-01 |
| 旧位置 | 页面、区块和大致滚动位置 |
| 观察内容 | 真实文字、数据、图片、链接 |
| 证据等级 | CODE、STATIC、RUNTIME、INTERACTION、USER、INFERENCE |
| 访客问题 | 这个区块试图回答什么 |
| 当前价值 | 信息、证据、导航、信任、装饰或未知 |
| 当前问题 | 重复、空泛、过时、缺证据、AI 味、过密等 |
| 新版目标 | Home、Archive、Now、About、Contact 或不迁移 |
| 处理建议 | 保留、重写、合并、移动、删除、暂缓 |
| 需要确认 | 事实、公开边界、意义或个人偏好 |
| 备注 | 缺少的素材和后续行动 |

### B-1. 结构问题

重点检查：

- Home 是否承担了过多内容；
- Projects 和 Works 是否重复；
- 项目列表和项目详情是否分层；
- About 是否只是重复 Home；
- Contact 是否只是链接堆；
- 是否存在没有真实内容支撑的区块；
- 哪些内容需要进入 Archive，而不是停留在 Home。

### B-2. 内容问题

重点检查：

- 事实是否仍然准确；
- 数据是否有时间范围和来源；
- 文案是否像 AI 生成的泛泛介绍；
- 是否有明显的“不是……而是……”等模板化句式；
- 是否把不同类型经历错误地包装成同一种项目；
- 是否有重复介绍；
- 是否有用户已经不想公开的内容；
- 是否有内容值得加入但旧网站没有展示。

### B-3. 视觉与表达问题

视觉审计只服务于排除问题，不用来决定新版样式。

重点记录：

- 暖橙、浅黄、暖绿等已经明确不喜欢的组合；
- 过度模板化的字体和标题；
- 过密文字；
- 没有真实内容支撑的装饰；
- 过度卡片化；
- 与个人经历没有关系的动效；
- 看起来像 AI 自动生成的句式和模块命名。

每个问题要附截图或源码位置，避免只写主观评价。

## 阶段 C：旧结构到新版的映射

### C-1. Home

重点判断：

- 旧 Hero 哪些事实可以保留；
- 旧数据卡片是否进入 Live Index；
- 旧“三件事”是否改成 Current Workbench；
- 旧精选作品如何按当前能力和真实结果重新选择；
- Contact 是否保留在 Home 末尾；
- 是否有不属于 Home 的内容需要移出。

### C-2. Projects 和 Works

重点判断：

- 哪些内容是项目；
- 哪些内容是内容作品；
- 哪些内容其实是经历；
- 哪些内容应该作为 Archive 的统一条目；
- 哪些条目只有列表卡片，哪些值得详情页；
- 旧分类是否造成理解成本。

初步建议不是把所有类型拆成独立页面，而是统一 Archive、使用有限的 type 字段。审计结果可以推翻这一建议，但必须有内容数量和访客理解上的理由。

### C-3. 第一个详情页

对英语教育产品与社群交付重点查找：

- 背景和开始原因；
- Maki 的具体职责；
- 交付范围和频率；
- 可公开的最终结果；
- 截图、记录、反馈或其他证据；
- 哪些结论目前不能证明；
- 是否需要匿名化；
- 是否适合作为新版详情页的模板。

### C-4. About

重点判断：

- 旧 About 中哪些经历仍然准确；
- 哪些段落只是抽象价值宣言；
- 能否提炼出几个真实转折；
- 内容表达、产品、系统和 AI 是否应该在 About 中建立联系；
- 哪些内容适合留在 Archive 的具体项目里。

### C-5. Contact

重点判断：

- 微信二维码是否能正常使用；
- 邮箱、GitHub 和社交账号是否仍然有效；
- 是否需要按项目合作、求职、普通交流排序；
- 哪些账号只适合作为辅助链接；
- 是否存在隐私或公开范围问题。

## 4. 两人的合作方式

### 4.1 我负责

- 读取旧网站代码和真实内容；
- 运行旧网站；
- 截图和检查交互；
- 建立页面和区块清单；
- 记录证据等级；
- 发现重复、过时、缺证据和 AI 味；
- 提出迁移建议；
- 把不确定事项集中整理给 Maki；
- 未经确认不修改生产代码。

### 4.2 Maki 负责

- 确认事实是否准确；
- 判断内容是否仍然代表现在的自己；
- 确定哪些内容可以公开；
- 决定保留、重写、合并、删除或暂缓；
- 提供源码无法推断的经历意义；
- 对截图和页面原型做最终“像不像我”的判断。

### 4.3 每一轮的交付方式

每轮不要求 Maki 阅读全部源码。我的交付应包含：

1. 一页结论摘要；
2. 关键截图；
3. 审计矩阵；
4. 建议处理方式；
5. 仍需 Maki 决定的问题。

Maki 可以用下面格式回复：

HOME-03：重写

保留：

删除：

原因：

或者：

ARCHIVE-02：事实待补充，暂不进入新版

## 6. 验收闸门

### Gate A：证据完整

满足：

- 五个旧页面已清点；
- 页面滚动结构已记录；
- 关键交互已检查；
- 桌面端和移动端有截图；
- 内容来源和证据等级已标注；
- 没有把推断写成事实。

Gate A 之前不修改生产代码。

### Gate B：迁移决定完成

满足：

- Home 的旧区块都有处理建议；
- Projects 和 Works 的合并方案有证据；
- 第一批 Archive 条目已确认；
- 第一个详情页的素材缺口已列出；
- About 和 Contact 的职责不冲突；
- 旧内容的保留、重写、删除和暂缓已经分开；
- Maki 已确认关键事实和公开边界。

### Gate C：可以进入新版实现

满足：

- Site Content Outline 可以更新为 v0.2；
- Archive 条目的最小字段已经确定；
- 第一个详情页的粗内容足够开始原型；
- Home 的区块顺序和主行动没有阻塞项；
- 亮色 Working Archive 第一条真实链路的实现范围明确；
- 暗色模式仍然不提前扩展到全站。

## 7. 当前已知风险和处理方式

### 风险一：把网站持续更新误写成个人定位

处理：

- 保留“持续更新”作为网站原则；
- 审计时继续寻找 Maki 的真实身份表达；
- 不在没有依据时生成新的职业口号。

### 风险二：Archive 条目字段过少

问卷中暂时没有勾选一句话摘要、证据、下一步和详情链接。

处理建议：

- 所有列表条目至少需要标题、类型、状态、时间、短摘要和角色；
- 证据、结果、下一步和详情页可以只对重要条目要求；
- 审计会根据不同条目类型确认字段是否适用。

### 风险三：四个 Archive 条目的类型尚未填写

审计阶段先使用临时分类：

- Maki English：CONTENT；
- 英语教育产品与社群交付：EXPERIENCE 或 PROJECT；
- AutoCoder 实习：EXPERIENCE；
- AdventureX 黑客松：PROJECT 或 EXPERIMENT。

这只是内部审计标签，不是最终页面文案。

### 风险四：Contact 只依赖微信

处理：

- 微信可以作为首选；
- 同时核验邮箱是否保留为清晰的备用入口；
- 不把二维码作为唯一联系方式。

### 风险五：旧代码重新影响新版审美

处理：

- 审计表增加“视觉问题”字段；
- 视觉问题必须附证据；
- 所有新版决策仍以 Design Baseline 和 Component Contract 为准；
- 旧网站不参与新的视觉方向选择。

## 8. 执行顺序

第一轮只审计旧 Home：

1. 路由和组件清点；
2. 运行时截图；
3. 按滚动顺序拆分区块；
4. 检查每个按钮、链接和交互；
5. 填写 Home 审计矩阵；
6. 输出 Home 审计摘要；
7. 交给 Maki 做第一次保留、重写、移动、删除判断。

Home 通过 Gate A 后，再审计 Projects 和 Works。

不要同时把五个页面全部拆完再让 Maki 第一次反馈。分页面交付可以尽早发现判断标准是否正确，降低返工。

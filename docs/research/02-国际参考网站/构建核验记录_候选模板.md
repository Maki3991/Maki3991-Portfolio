- 克隆目录：`output/research-clones/`

## SDBurt

执行命令：

```text
pnpm.cmd install --frozen-lockfile
pnpm.cmd build
```

依赖安装成功，实际使用 pnpm `10.28.0`。安装时出现：

```text
WARN Unsupported engine: wanted: {"node":">=22.12.0 <23"}
current: {"node":"v24.16.0","pnpm":"10.28.0"}
```

随后 `astro check` 和 `astro build` 均成功：

```text
Result (38 files):
- 0 errors
- 0 warnings
- 0 hints
18 page(s) built
```

构建判断：项目本身的静态构建链条是通的；如果采用，应先为项目锁定 Node 22.12.x，而不是把当前 Node 24 当作兼容性证明。

## Astro Kami

执行命令：

```text
pnpm.cmd install --frozen-lockfile
pnpm.cmd build
```

依赖安装成功，实际使用 pnpm `10.19.0`。安装阶段出现 pnpm 的构建脚本提示：

```text
Ignored build scripts: esbuild.
Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
```

`astro check` 没有 error，但有 17 个 hint，主要来自 `astro:content` 中 `z` 的弃用提示，以及复制按钮使用的 `document.execCommand` 弃用提示。生产构建成功：

```text
43 page(s) built
Indexed 2 languages
Indexed 10 pages
```

构建还执行了 OG 图片生成/压缩、HTML/图片/JavaScript 压缩和 Pagefind 索引。构建判断：模板的能力确实可用，但它把国际化、数学、OG 图片、压缩、搜索、评论/分析扩展等维护面一起带进来了；对本项目首版来说，应该拆取内容模型与页面结构，而不是整体复制。

## hmbldv

执行命令：

```text
npm.cmd ci
npm.cmd run build
```

依赖安装成功，但 npm audit 报告：

```text
18 vulnerabilities (2 low, 2 moderate, 12 high, 2 critical)
```

没有执行 `npm audit fix`，因为那会改变研究副本的依赖状态，且不属于本次核验范围。

生产构建失败。Astro 首先报告：

```text
The base directory ... src/content/wiki/ does not exist.
```

随后示例项目的数据不符合 schema：`example-project` 的 `category` 使用了 `web-development`，而 schema 只接受 `aws-security`、`aws-infra`、`homelab`、`ai-tools`、`local-dev`、`aws-ai`、`frontend-development`。

构建判断：这个仓库仍可作为内容模型和文档式项目详情的参考，但不能在未修复示例内容与 schema 之前把它评为“可直接使用”。这也验证了本研究中“真实构建证据高于 README 宣称”的原则。

## 对当前项目的采用建议

1. 先参考 SDBurt 的内容集合和设计 Token，但不要复制其运行时版本；建立 Node 版本策略后再决定是否采用 Astro 7。
2. 从 Astro Kami 拆取文章详情、Showcase、标签、RSS 和配置集中化思路；暂时不引入完整国际化、OG 图片和 webmentions 链路。
3. 将 hmbldv 的项目版本/提交历史视为可选信息模型，只有当真实内容需要时才加入；不能把它当作已验证的模板底座。
4. 下一阶段若要继续本地验证，应该先在当前项目分支建立最小内容集合和 Token 原型，再做迁移成本比较，而不是继续无止境扩大模板列表。

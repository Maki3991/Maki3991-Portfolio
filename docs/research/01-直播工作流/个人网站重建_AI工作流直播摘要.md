# 个人网站重建：AI 协作工作流直播摘要

> 用途：给后续负责重建个人网站的 agent 作为背景上下文。本文是对两场直播逐字稿的压缩整理，不是主播的逐字引用，也不是已经验证过的前端设计规范。涉及主播自评的数字、工具能力和未来推演，必须按“主播观点”处理。

## 主播真正要解决的问题

主播做的不是一个一次性名片或演示 Demo，而是希望长期使用 5–10 年的个人网站：未来可以承载文章、专题、人生时间线、当前正在做的事、项目进度、健身/生活数据、作品、视频、RSS 等。网站既对外展示，也要成为本人可以使用的个人信息入口。

他反复强调：看到别人用模板、提示词或 agent 复刻出漂亮页面，不等于自己掌握了“稳定做出这类质量”的能力。目标不是找到一个神奇模板，而是建立一套在不知道前端术语、也不擅长描述视觉细节时，仍能持续产出合适网站的协作系统。

## 实际工作流

### 1. 先设计协作系统，不让 AI 直接生成全站

一开始先告诉 agent：目标是长期使用的真实网站，暂时不要直接写页面，也不要迷信现成的前端设计 skill。先研究“怎样让一个不懂前端的人与 AI 稳定协作并做出高质量网站”。

这一步的重点是把目标从“生成一个页面”改成“建立一套可重复的生产和验收流程”。

### 2. 让 AI 做宽范围调研，解决“我不知道去哪儿看”

调研范围包括模板/成品网站、动效库、组件库、设计规范、设计师与甲方沟通方式等。主播让两个 agent 汇总来源、社区评价、优点、适配程度、排序和评分，并产出调研报告与方法文档。

为了补足通用社区调研的偏差，主播自己在小红书按关键词搜集了约 50–80 个相关帖子链接（逐字稿另有约 80 个的说法），交给既有流程提取：

- 可继续浏览的优质网站/资源入口；
- 帖子中提到的截图、录屏、抓组件、定义风格、向 AI 传递视觉意图等方法。

这里的原则是：AI 负责扩大搜索和整理范围，人负责判断哪些入口与自己的语境、平台和目标相关。

### 3. 用真实页面选择审美，不先学习术语

AI 先从调研结果中筛出 3–5 个候选网站。主播通过实际浏览页面和交互来选择，而不是先写一篇专业设计说明。他看几十个页面，留下大约 10 个主要参考，另加自己喜欢的个人网站，逐字稿中出现“10 个”和“12+2=14 个”两种数字，不能当作精确统计。

为了避免只看首页，主播要求 agent 点击参考网站中的按钮、导航和页面，把可见状态截图并分析共性，最后沉淀出一版属于自己的 Design System：整体色彩、排版、圆角/边界、动效克制程度、组件倾向和内容呈现方式。

核心技巧：主播不需要准确说出“我要某种导航/目录/动效曲线”，他只需要看几个可视化结果并判断喜欢、不喜欢、保留什么、融合什么。视觉选择比贫乏的文字描述更可靠。

### 4. 把网站拆成设计维度，建立 `lab / laboratory`

主播让 agent 先拆解“个人网站有哪些可独立设计和验收的部分”。维度数量经历了 28 → 47 → 62 等不同阶段的扩展；这些数字是阶段性口述，不是固定规范。

每个维度不直接定稿，而是在实验室页面里生成约 5 个可以实际预览/交互的变体。展示过的维度包括：

- Hero/首页开场、导航、全屏菜单、按钮和胶囊交互；
- 文章阅读版式、TOC/目录、阅读进度、专题/标签/年份视图；
- 状态面板、当前正在做什么、目标进度、倒计时、贡献热力图；
- 字体排印、中英文混排、引用、代码块、代码多窗口、表格；
- 视频、照片墙、分享卡、命令面板、搜索、404、微交互、光效。

主播逐个看变体并选择。一个变体有可取之处但不完整，就要求“基于这个版本再生成 5–10 个”，然后融合不同版本的优点。这样把“不知道自己要什么”转化为“看见候选后能判断什么更接近我”。

### 5. 先局部打样，再展开全站

先用首页/特定 Hero 等局部页面验证大方向，而不是直接生成几十个页面。局部样板的作用不是立刻达到最终质量，而是确认 agent 对风格的理解大体正确。

主播提出的“好东西是改出来的”意味着：风格方向先定，细节通过一轮轮可视化候选、选择、融合和局部修改得到；不要期待一次 prompt 直接产出完善全站。

### 6. 每个板块按固定五步落地

主播发现 agent 会在大任务里偷懒，因此要求每个板块单独执行：

1. 扫描当前板块/页面的实现；
2. 重新读取设计库，确认整体风格；
3. 查看该板块已选的参考方案及对应代码/样例；
4. 找出当前网站中需要修改的具体位置；
5. 把所有不确定处先列出来与人确认，确认后再改。

改完一个板块先审核、微调、融合，再进入下一个。这样修改天然局部化：说改哪个组件就改哪个组件，尽量不牵连其他页面，避免“改 A 错 B、越改越乱”。

### 7. 一周后的实际运行方式

下篇展示的约 80% 可用版本，是在一周的“旁路工作”中完成的：优化对话挂在副屏，约有五六十项组件/维度或页面优化；主播主要推进下一项、打开页面看结果，有问题就截图或语音反馈，然后继续主线工作，agent 在旁边思考和修改。每项通常一两次反馈，最多再来一版，再进入下一项。

每轮确认后的反馈、参数和选择会回写设计系统文档。主播自评整体黑白、克制、统一，动画没有无节制堆叠；但展示中仍有占位内容、分辨率适配和细节未完成，不能把“80% 可用”理解成通过了完整的发布验收。

### 8. 内容填充依赖已有上下文，但必须核实事实

主播的设想是：agent 已经通过长期工作区和历史协作了解他的经历、资源、项目和表达方式，因此网站内容大多可以先由 agent 起草，只有不确定处再用短访谈补齐。对我们的项目，不能直接照搬这一点：任何个人经历、项目结果、数据、评价和链接仍需逐项以本地资料或用户确认作为真源。

## 人与 AI 的分工

### 人负责

- 长期目标、范围、优先级和不可妥协的约束；
- 参考网站的选择、整体方向和视觉判断；
- 从多个候选中取舍，指出关键误区和需要融合的元素；
- 内容真实性、隐私边界、是否值得继续打磨；
- 关键节点的方案/流程验收，而不是逐行指导代码。

### AI 负责

- 宽范围检索、分类、去重和方法文档整理；
- 把网站拆成设计维度；
- 在既定风格下生成可预览的多个变体；
- 组件/页面代码实现、局部修改和重复性检查；
- 将已确认的参数、截图、代码索引和决策沉淀到文档。

主播自认为人当前仍更擅长基于视觉做整体风格判断；AI 更擅长规模化发散、专业细节和重复执行。人不必假装知道每个专业术语，但必须在关键判断点停下来。

## 可迁移的心法与控制原则

1. **先设计流程，再做产出。** 大多数返工不是某个局部技术点导致，而是一开始没有想清楚目标、边界、阶段和验收方式。
2. **区分“稳定执行”和“智能发散”。** 调研整理、代码落地、局部改动需要明确步骤和稳定性；组件创意、参考方案和灵感需要允许 AI 发散。两类工作不能用同一种协作方式。
3. **方案不能盲信。** AI 给出的方案看起来完整，不代表方向正确；流程和方案设计是人最应该认真阅读、质疑和重构的地方。
4. **把不确定性放到可控的选择界面。** 不要求人用贫乏语言描述脑内画面，而让 AI 先做多个可视化候选，人用视觉反馈选择；选定后再收窄约束并执行。
5. **先大方向，后局部细节。** 大方向一致后，组件由同一设计系统重新实现；参考效果可以借鉴，但不要把别人网站的代码硬抄进来再强行改风格。
6. **局部改动、逐项验收。** 每次明确修改对象和影响范围，改完看页面，保留截图/反馈，确认后再推进下一项。
7. **抓少数高价值判断。** AI 可以完成大量“不会错但普通”的工作；人要集中注意力找出真正影响结果的少数问题，不能把时间平均花在所有细节上。
8. **把项目产出变成复利资产。** Design System 不只写形容词，还应包含组件规范、参数、决策理由、可复用截图和对应代码索引；以后其他页面、封面、PPT 或前端工具可优先复用它。
9. **让工作区有全局记忆。** 主播提倡一个跨项目的 work station/工作区，集中保存协作协议、个人资料、设计系统和决策记录，避免每个项目都从白板开始。具体目录和权限要按本地项目实际情况设计。
10. **沟通应越用越短，但不是一开始就少说。** 先通过真实项目把偏好、判断和规范沉淀清楚，之后才可能用一句“按我的设计系统处理”稳定复用。

## 对本次个人网站重建的直接启发（这是基于直播内容的推导，不是主播原话）

- 不要从“把现有网站整体改得更有设计感”开始。先审计当前页面、内容、组件和“AI 味”具体出现在哪里，形成可验收的问题清单。
- 先做一个小型参考/方向实验室：用少量真实参考验证你喜欢的气质、密度、颜色、排版和动效边界，再决定全站结构。
- 先选择 1 个核心页面或一个组件链路做真实落地，确认方向、反馈方式和局部修改不会污染全站，再扩大到小批量页面。
- 每次修改都留下“为什么选它、改了什么、哪些地方不要动”的记录；稳定的视觉决策最终应沉淀成项目自己的设计基线。
- 交付判断要分层：代码已实现 → 静态检查 → 页面可访问 → 单页真实验证 → 小批量页面验证 → 响应式/可访问性/性能/安全/内容事实检查。直播中的“80%/85 分/90 分”不能代替这些验证。

## 证据边界与风险提醒

- 逐字稿能证明主播描述并展示了这套方法及部分页面，不证明最终网站已经通过跨设备、性能、无障碍、安全或长期维护验证。
- “15% 验证”“80% 完成”“85 分以上/90 分以上”等是主播的阶段性自评。
- 参考网站数量、设计维度数量、模型/工具名称存在口述或转写不一致；新 agent 不应据此断言精确数字或具体产品能力。
- 直播中关于隐私、医疗、伦理、未来技术和“同模型同系统结果必然相同”等内容属于主播个人判断；本项目只吸收其中的工作流启发，不把这些判断当成事实或安全建议。
- 任何密码、API Key、金融账号和敏感个人资料都不能明文写进 Markdown、仓库或网站。若以后需要让 agent 调用，应使用本地密码管理器、环境变量、最小权限和人工确认。

## 给新 thread 的启动指令

你正在协助重建一个已有 Astro 静态个人网站。用户不喜欢当前网站明显的 AI 模板感。请先读取本文件，再检查仓库现状、现有页面、内容真源和 Git 状态；不要直接全站重写。先提出一个小范围、可预览、可验收的方向实验，并把每个关键视觉决策记录下来。任何涉及用户经历、项目成果、数据和链接的内容，都必须区分本地证据、用户确认、推断和待补信息。完成一项再进入下一项，并在每个阶段报告：当前 gate、已完成、证据级别、失败/不确定点和下一 gate。

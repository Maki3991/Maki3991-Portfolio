## 目的

这份文档记录个人网站在“大方向、Component Lab 和初版选择”完成之后的实际实施方法。

核心原则是：

> 页面负责提供上下文，组件或设计维度负责迭代；一次只处理一个明确的组件切片，最后再做页面和全站联调。

它修正了早期“以整个页面为最小实现单位”的工作流。页面级审计仍然有用，但不能把一个 Home 页面一次性当成一个大任务全部实现。

## 原文依据

王振宇在原始分享中明确了以下做法：

- 先让 AI 逐个检查参考网站的可点击元素，点击后截图并分析，而不是只记首页印象。见上篇 `35:23`；
- 先只用 Home/Hero 样板验证大方向，再把网站拆成约 62 个可独立判断的设计维度，每个维度生成 5 个可预览方案。见上篇 `38:00`、`45:31`；
- 发现 AI 一次性全站修改会偷懒后，改成“一个一个来”，每个板块执行五步。见上篇 `1:14:25`；
- 一周后的实际工作是五十多轮，每轮处理一个板块状态，修改后只检查受影响的页面，再进入下一轮。见下篇 `19:14`、`22:42`；
- 每个组件完成后，把文字规则、具体代码和必要截图一起沉淀到设计系统。见下篇 `1:19:09`、`1:19:45`。

## 整体工作流

```text
目标与内容边界
    ↓
参考网站调研与逐站交互审计
    ↓
设计方向样板：只验证大方向
    ↓
Component Lab：每个维度生成多个可运行方案
    ↓
用户选择、备注和融合
    ↓
组件级实施循环：一轮只改一个组件/设计维度
    ↓
页面组合与跨组件联调
    ↓
全站验收与长期设计系统沉淀
```

### 页面在其中的三个角色

1. **方向样板**：最初用 Home/Hero 验证整体风格是否大致正确；这不是最终页面。
2. **影响范围容器**：实现某个组件时，页面用于确认它出现在哪些页面、是否破坏上下文。
3. **最终组合对象**：所有主要组件完成后，再检查区块秩序、重复、间距、响应式和跨组件联动。

因此，“页面级”与“组件级”不是二选一：页面用于观察整体，组件/设计维度才是主要的修订单位。

## 什么算一个实施单位

这里的“组件”不是只指 Button 或 Card 等原子元素，而是一个可以独立描述、实现、验收的视觉或交互切片，例如：

- Page Shell / Section Rhythm：容器、最大宽度、网格、区块间距、分隔线；
- Header / Navigation；
- Hero；
- Live Index；
- Current Workbench 行；
- Selected Work；
- Contact 入口；
- Footer；
- 文章阅读版式、目录、代码块、表格、图片展示或动效语言。

一个设计维度可能影响多个页面。例如 Header 不能只在 Home 上改完就算完成；文章阅读版式也可能同时影响多个详情页。

## 单个组件的循环

### 0. 选定范围

明确本轮只处理一个组件或设计维度，并写出：

- 本轮要解决的问题；
- 可能受影响的页面；
- 本轮不处理的相邻问题；
- 采用的已选 Lab 方案编号。

### 1. 扫描当前实现

Agent 只读检查：

- 当前组件的 Astro/HTML 结构；
- 数据来源和真实内容；
- CSS、交互脚本和响应式规则；
- 该组件在所有受影响页面的出现位置；
- 当前截图、控制台、溢出和已知问题。

这一步的目标是知道“现在是什么、改动会影响哪里”，不是马上提出新设计。

### 2. 重新读取设计库

Agent 重新读取当前有效的：

- `Design Baseline`；
- `Component Contract`；
- 对应的站点架构和内容边界；
- 必要时的旧站内容审计。

需要说明本轮适用的字体、颜色、容器、间距、边框、动效、状态和响应式规则，以及明确不能继承的旧风格。

### 3. 查看已选参考和代码样例

Agent 必须同时查看：

- 用户已经选中的组件方案；
- Lab 中对应的真实可运行样例和代码入口；
- 产生该方案的参考网站中与本组件有关的结构或交互。

Lab 代码是硬性参考，不代表应该整页复制。重点是理解组件的结构、状态和效果，再用当前生产架构重新实现；不要把未选中的 Lab CSS 偷渡进生产代码。

### 4. 定位具体修改位置

列出准确的：

- 页面文件；
- 共享组件；
- CSS/token 文件；
- 数据文件；
- 图片、链接或脚本；
- 受影响页面；
- 不应被改动的相邻区域。

这一步必须把“我要改 Header”具体化为“改哪个组件、哪些选择器、哪些页面会看到变化”。

### 5. 判断是否存在需要用户取舍的事项

Agent 在写代码前先自行判断所有不确定处。只有会改变视觉结果、内容事实或修改范围的问题，才需要交给用户取舍，例如：

- 两个已选方案如何融合；
- 某个组件是否在 Home 使用；
- 是否加入某个动效或状态；
- 真实内容不足时是否保留该结构；
- 修改共享组件是否会影响其他页面；
- 当前视觉问题是实现错误还是选择本身不合适。

如果没有上述重大不确定项，Agent 完成前四步后直接实现。用户不需要阅读源码，也不需要审批技术实现；用户只在真实结果出现后反馈视觉、内容或行为问题。

## 实现与验收

没有重大不确定项时，Agent 直接进入实现；如果确实需要用户取舍，则只暂停当前组件，不扩大范围：

1. 只修改当前组件及明确依赖；
2. 不顺手扩展其他页面、组件或暗色模式；
3. 先在受影响页面上验证，再进入下一个组件；
4. 有问题时优先给出截图或准确描述，进行局部返工；
5. 不用一次性重写整个 Home；用户不需要审阅源码 diff。

每轮至少验收：

- 受影响页面的桌面端截图；
- `390 × 844` 左右的移动端截图；
- 横向溢出；
- Hover、Focus、Click、展开和键盘行为（如果本轮涉及）；
- 长标题、中文英文混排和缺少内容时的状态；
- 浏览器控制台；
- `npm.cmd run build`。

验收通过后，才把该组件标记为 `implemented`，并进入下一个组件。

## 每轮要沉淀什么

每个通过验收的组件都要回写到 Component Contract 或其后续版本：

| 内容 | 记录方式 |
|---|---|
| 选择结论 | 组件编号、方案编号、用户备注和融合关系 |
| 软性规则 | 组件应该给人的感觉、内容层级、使用禁区 |
| 硬性规则 | 颜色、字体、尺寸、间距、状态和响应式规则 |
| 代码入口 | 生产组件、样式、数据和脚本文件路径 |
| 视觉证据 | `output/playwright/` 中的截图路径 |
| 验收状态 | `implemented`、`needs review` 或 `superseded` |
| 未决问题 | 下一轮必须知道的遗留事项 |

设计系统的价值不是只有一段风格描述，而是“软性语言 + 经过验收的具体代码 + 必要截图”的组合。

## 页面组合与最终联调

组件级循环完成后，才进行页面级检查：

- 页面区域顺序是否清楚；
- 区块之间是否有足够的分界和节奏；
- 主次层级是否明确；
- 同一组件是否重复过度；
- 各组件组合后是否产生新的冲突；
- 桌面、移动端和键盘路径是否完整。

这一步是组合验收，不是重新把所有组件混在一起设计。

## 当前项目的执行状态

当前 Home 的代码属于：

> `rough composition / needs component-level review`

它证明了数据入口和基本区块可以运行，但不代表最终视觉已经接受。当前“组件统一但页面混乱、板块边界弱”的问题，应先按下面顺序处理：

1. **Home Page Shell / Section Rhythm**：容器、网格、区块分界、间距和标题层级；
2. **Header / Navigation**；
3. **Hero**；
4. **Live Index**；
5. **Current Workbench**；
6. **Selected Work**；
7. **Contact**；
8. **Footer 与跨组件响应式联调**。

第一轮不继续新增组件、不开始暗色模式、不实现 Archive Detail，也不把当前粗略 Home 当成新的 Baseline。

## 失败与返工规则

发现问题时先分类：

1. **实现问题**：结构、CSS、响应式或交互错误；修生产代码，不推翻选择。
2. **内容问题**：事实、文字、图片或公开边界不成立；回到内容确认，不用占位内容掩盖。
3. **组件组合问题**：单个组件没问题，但与相邻组件冲突；只调整当前组合关系或页面 Shell。
4. **视觉选择问题**：已选方案本身不适合真实内容；保留旧决定和截图，重新打开该组件的 Lab 方案，形成新版本记录。
5. **全局方向问题**：只有多个组件持续冲突时，才重新讨论 Baseline；不能因为一个页面不好看就推翻全站方向。

# Design Baseline v0.2：Working Archive / Light-first

## 文档状态

- **状态**：当前有效，待进入第一条 Astro 真实链路实现
- **版本**：v0.2
- **日期**：2026-09-14
- **用途**：给没有本轮对话上下文的 agent 使用的设计与实现边界合同
- **前一版本**：[Design Baseline v0.1](../04-Design-Baseline-v0.1/design-baseline-v0.1-reference-audit.md)

这份文档更新的是“方向确定之后的执行约束”，不是对 v0.1 研究证据的覆盖。v0.1 继续保留参考网站、交互证据和初始原则；本版本只记录已经经过 Maki 选择的方向、原型证据和下一阶段的实现规则。

## 0. 如果只记住十句话

1. 这是一个长期维护的个人工作档案，不是一次性的简历页、作品海报或个人 Dashboard。
2. 主要视觉方向是 **Working Archive**：先让访客看见 Maki 正在做什么，再看项目证据和工作方法。
3. 亮色是默认开发对象；暗色是同一套设计系统的第二主题，不是另一套页面。
4. 风格应像冷静、清晰的编辑部索引或个人工作台：有秩序，但不能像企业后台。
5. 内容、编号、细线、状态和真实证据比装饰更重要。
6. 默认使用无衬线正文；元信息可以使用等宽/窄标签；不要回到暖色衬线体。
7. 项目、作品、文章和未来栏目优先使用同一种列表行和详情结构。
8. 新增栏目时优先新增内容记录和已有 index/detail 关系，不重新发明一套 UI。
9. 不使用大面积渐变、玻璃拟态、无意义数字、滚动劫持或复杂动效作为核心体验。
10. 在亮色第一条真实链路验收前，不扩展全站；在全站扩展前，暗色主题必须在同一条链路上通过验收。

## 1. 决策状态和证据

本文件使用三个状态标记：

- **[LOCKED]**：Maki 已经选择，后续 agent 不应重新发散；如需改变，必须先报告冲突。
- **[PROVISIONAL]**：原型中已经使用，第一条真实链路需要验证；可以微调，但不能无理由换方向。
- **[OPEN]**：尚未决定，agent 不应擅自锁死。

### [LOCKED] 已确定

- 站点长期目标：展示真实身份、项目、作品、思考和合作方式，并能持续更新多年。
- 首页主方向：Working Archive。
- 默认开发主题：亮色。
- 主题关系：暗色沿用同一信息架构、组件和内容，不创建另一套页面。
- 信息顺序：当前状态 → 项目/作品 → 项目证据与方法 → Writing / Notes → About / Now → Contact。
- 视觉排除：暖色衬线体、橙/绿/淡黄常见组合、模板化 AI 文案、虚假指标、Dashboard 化的数据堆叠、复杂动效作为导航。

### [PROVISIONAL] 原型已经验证但要在真实页面复核

- 浅色背景使用冷浅灰/蓝灰纸面；暗色背景使用深石墨而非纯黑。
- 主要强调色使用受控蓝色；青色只作为少量状态信号。
- 顶部采用细 Header 和文字导航；移动端折叠为 `MENU`。
- 首屏采用左侧身份和定位、右侧 Live Index 的双栏结构；移动端改为单栏。
- 项目和文章使用有编号的列表行；一条记录可以进入详情。
- 项目详情使用 `Role / Results / Method / Next` 等事实字段，而不是长篇口号。
- 使用少量真实图片作为证据入口，不把图片装饰化或做成照片墙。

### [OPEN] 仍需后续决定

- 最终字体及其中文 fallback；
- 具体色值、圆角、阴影和间距数值；
- 主题切换是手动按钮、跟随系统，还是两者结合；
- Projects 与 Works 最终分成两个入口，还是统一为一个内容集合；
- Writing / Notes 的公开 URL；
- About 是否独立成页；
- Now、Experiments、Learning、Life 等未来栏目何时拥有独立入口。

## 2. 设计简报：页面应该让人感受到什么

### 应该感受到

- 这是一个正在生长的个人工作档案；
- Maki 有具体做过的事情，不只是自我介绍；
- 内容可以继续增加，但页面规则不会随之失控；
- 视觉冷静、克制、可阅读，同时保留一点个人识别度；
- 访客可以快速定位项目、作品、笔记和联系方式。

### 不应该感受到

- 一页做完就不再更新的个人名片；
- 套模板生成的“设计师个人主页”；
- 企业 Dashboard、数据监控台或 SaaS 后台；
- 为了显得高级而堆叠的渐变、玻璃、发光、超大圆角和数字；
- 一堆正确但空泛的 AI 自我介绍。

## 3. 信息架构和页面职责

### 第一条真实链路

第一阶段只实现能验证完整体验的最小链路：

1. **Home / Working Archive**：身份、当前状态、精选项目/作品、最新 Notes、About / Contact 入口；
2. **Projects / Works index**：至少能够继续增加真实条目；
3. **一个真实 project / work detail**：使用现有英语自媒体项目和四级六级听力作品内容；
4. **Writing / Notes 入口**：可以先是 Home 区段或一个最小索引，不提前制造空页面；
5. **About / Contact**：稳定身份、寻找方向和真实联系方式。

### 内容优先级

1. 当前正在做什么；
2. 项目和作品证据；
3. 如何做事、如何复盘；
4. 个人经历和合作方式；
5. 联系入口。

### 首页不负责什么

首页不需要承载所有未来栏目，不要为了“看起来完整”放空的 Fitness、Life、RSS、实时 GitHub 或个人 Dashboard 区块。没有真实内容的栏目不显示；有内容之后复用既有列表/详情原语。

## 4. 布局语法：页面由什么组成

### 4.1 全局结构

- 顶部有一条轻量实验/版本信息时，只出现在实验室预览，不进入最终生产站点；
- 生产页面使用清晰的 Site Header、Wordmark、主导航和移动菜单；
- 页面主体有统一的水平内容轨道和可阅读的最大宽度；
- Section 之间使用一致的垂直节奏和细线，不用每个区块换一种视觉语言；
- Footer 提供回到顶部、版权和真实联系/外部链接。

### 4.2 Home / Working Archive

- 首屏左侧：身份、headline、当前定位、简短 intro、主要行动；
- 首屏右侧：`ROLE / STUDY / LOCATION / SEEKING / NOW` 的 Live Index；
- 首屏之后：Current status / Now 信号，然后进入项目和作品列表；
- 项目列表中数字是内容索引，不是装饰性 KPI；
- Writing / Notes 以列表行或轻量条目出现；
- About / Contact 是明确入口，不用空泛的“改变世界”式结尾。

### 4.3 Item row

一条可追加的记录至少能表达：

- `index`：编号；
- `type / category`：PROJECT、WORK、NOTE 等；
- `date / year / status`：时间或当前状态；
- `title`：具体名称；
- `summary`：一句话说明；
- `evidence`：结果、平台、链接或可核验材料；
- `next`：如果是项目，可说明下一步；
- `link`：进入详情或外部来源。

### 4.4 Project detail

短项目不必填满所有章节，但优先按以下顺序组织：

1. Context / 背景；
2. Role / 我负责什么；
3. Decisions / 关键判断；
4. Process / 做法；
5. Results / 结果和证据；
6. Reflection / 复盘；
7. Next / 后续。

## 5. 视觉语法

### 5.1 色彩不是一组 Hex，而是一组语义角色

实现时应该使用语义变量，而不是在各组件里直接写颜色：

```text
background       页面背景
surface          普通区块/索引表面
surface-raised   详情或悬浮表面
text             标题和正文
muted            次要说明
line             分隔线
accent           编号、链接、主要行动
accent-strong    hover、active、focus 的强调状态
focus            键盘焦点
```

亮色和暗色分别给这些角色赋值。原型中使用过的值只作为 `[PROVISIONAL]` 起点：

| 主题 | 背景 | 表面 | 文字 | 强调色 |
|---|---|---|---|---|
| Light prototype | `#eef2f7` | `#f7f9fb` | `#142032` | `#315cdc` |
| Dark prototype | `#0b1017` | `#111923` | `#edf3fb` | `#7f9dff` |

这些值不能脱离截图直接复制到所有组件；必须在真实内容、弱文字、细线、按钮、focus 和图片上复核对比度。最终色值仍是 `[OPEN]`。

### 5.2 字体和排印

- 正文优先使用可长时间阅读的无衬线字体；
- 中文和英文混排时保持稳定的字面高度、行距和重量；
- 小标签、日期、状态和编号可以使用等宽或窄的元信息字体；
- 大标题可以有明显比例，但不要依靠暖色衬线体制造“高级感”；
- 正文、项目摘要和行动链接不能缩到难以阅读的尺寸；
- 不使用全大写长句作为主要正文。

### 5.3 形状、密度和图像

- 细线和留白负责建立秩序；
- 默认使用列表行，不把所有内容卡片化；
- 圆角保持克制，只在图片、必要的交互表面或明确的容器上使用；
- 阴影不是默认层次手段，只有浮层或菜单需要时使用；
- 每个页面最多有少量表现性图片，图片必须服务于作品/证据，不是装饰占位；
- 数据数字必须能解释来源和意义，不能为了填空制造指标。

## 6. 组件契约

这些是优先复用的组件原语，不是要求现在全部实现完：

| 组件 | 责任 | 不应该做什么 |
|---|---|---|
| `SiteHeader` | Wordmark、桌面导航、移动菜单、主题入口 | 不承载复杂全屏动画 |
| `SectionLabel` | 编号、分类、状态和章节语义 | 不用来制造装饰性噪音 |
| `ArchiveRow` | 项目、作品、文章和未来栏目的一致入口 | 不因内容类型不同重新设计一套结构 |
| `IndexList` | Role、Study、Now 等结构化事实 | 不做实时 Dashboard |
| `ProjectDetail` | 背景、角色、结果、方法、下一步 | 不写成未经事实支持的宣传文案 |
| `NoteRow` | Writing / Notes 的轻量索引 | 不要求每条都先成为长文章 |
| `Tag / Status / Year` | 真实分类和状态 | 不添加虚假的能力标签 |
| `ThemeToggle` | 亮暗主题切换和状态反馈 | 不改变内容层级或页面结构 |
| `Focus / Back to top` | 键盘和长页基本可用性 | 不依赖 hover 才能完成操作 |

实现后要补充“组件 → 代码文件 → 截图/路线”的索引，但不要把完整组件源码复制进本 baseline。

## 7. 文案和内容规则

- 用第一人称、具体事实和短句；
- 优先写项目做了什么、承担什么、结果是什么、下一步是什么；
- 删除模板化的“不是 A，而是 B”、空泛价值宣言和未经核验的数字；
- 任何经历、结果、评价、链接都必须回到 `src/site-content/`、`src/data/`、`public/assets/` 或用户确认；
- 实验中可以出现 `DRAFT / TO BE ADDED`，生产页面不能用占位内容填空；
- 新栏目优先新增内容集合和已有的 index/detail/list 关系，而不是复制一整页 HTML。

## 8. 亮色与暗色主题策略

### 8.1 开发顺序

1. 亮色先作为主要开发对象，确认结构、内容密度和阅读体验；
2. 完成 Home + 列表 + 一个详情 + Notes/About/Contact 的第一条真实链路；
3. 在这条链路上接入暗色主题，检查同一内容在暗色下是否成立；
4. 两个主题都通过桌面、移动、键盘和对比度验收后，再扩展全站页面。

不要等所有页面做完后再整体“换成暗色”；也不要在还没确认亮色结构前并行制作两套完整页面。

### 8.2 主题实现规则

- 主题只改变语义 token，不改变页面信息架构；
- 亮色为默认首屏，主题切换方式为 `[OPEN]`；
- 主题切换后保留当前路由、滚动位置和可见内容；
- link、hover、active、focus、disabled、细线和弱文字都要有两套可读状态；
- 图片可以根据需要调整边框或亮度，但不能因为主题切换而丢失信息；
- `prefers-reduced-motion` 下主题切换和菜单仍然直接完成，不依赖动画。

## 9. 动效、响应式和可访问性边界

### 动效层级

- **L0 默认**：颜色、下划线、透明度、小图标位移、focus/press 反馈；
- **L1 谨慎使用**：移动菜单、主题切换、短淡入/淡出，约 120–220ms；
- **L2 需要证明信息价值**：阅读进度或轻量章节定位；
- **L3 第一版排除**：Canvas/WebGL、滚动劫持、复杂全屏转场、依赖连续滚动才能理解的叙事。

### 验收要求

- 桌面和约 `390 × 844` 移动视口均可读、可操作；
- 移动端不出现水平溢出；
- 桌面导航和移动菜单都可使用；
- 重要链接、菜单、主题入口可键盘聚焦；
- 内容不依赖 hover 才能被发现；
- reduced-motion 下仍保留完整内容和操作路径；
- 真实内容和指标来源可追溯；
- 页面没有为了视觉效果制造空栏目、假数据或占位评价。

## 10. 第一条实现链路和工作协议

### 实现范围

第一轮只改亮色主版本，范围为：

- Home / Working Archive；
- 共享 Header 和移动导航；
- Projects / Works 的最小列表；
- 一个真实项目/作品详情；
- Writing / Notes 的最小入口；
- About / Contact 的真实内容区段。

暗色主题在亮色链路通过后接入同样的页面，不先扩大其他栏目。

### 每个板块的五步协议

1. 扫描当前实现和内容真源；
2. 重新读取本 baseline 与对应的原型截图；
3. 对照原型，确认要复用的结构和需要放弃的旧样式；
4. 列出具体修改文件、影响范围、不确定项和验收方式；
5. 只实现当前板块，浏览器验收并记录结果后，再进入下一个板块。

当前旧版 `src/styles/global.css` 中的暖色衬线视觉属于旧实现，不能作为新方向的默认继承来源。正式改动前应先确认共享样式和 BaseLayout 的迁移边界，不要直接全站替换或复制实验室静态 HTML。

## 12. 当前下一道闸门

先进行只读源码审计，形成一份迁移清单：

- 当前 Home、Header、全局样式和页面组件如何组成；
- 哪些内容已经由 Markdown / JSON 驱动；
- Projects、Works、About、Contact 的现有路由与可复用组件；
- 新 Working Archive 结构会替换什么、保留什么；
- 主题 token 应放在现有 `global.css` 还是拆成共享 theme 文件。

审计完成并确认边界后，才开始第一条亮色真实链路。不要在没有这份清单的情况下直接全站重构。

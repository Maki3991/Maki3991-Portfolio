# Now Article UI 工作流 v0.1

状态：当前有效 / 设计准备阶段

## 1. 目标

把 Now 页面从“能够渲染 Markdown”推进到“能够稳定展示真实 Now 文章”的生产页面。

本轮的设计对象不是一套新的全局设计系统，而是：

- Now 页面如何承载一篇当前文章；
- Markdown 正文如何形成稳定的阅读节奏；
- 日期标题、正文、分隔和页面出口之间如何建立关系；
- 桌面端和移动端如何保持同一种页面语气。

## 2. 已知约束

### 2.1 已锁定的全局规则

直接复用 Foundation 和 Component Contract，不重新做 5 选 1：

- Cold Index 配色语义；
- Quiet Editorial 字体角色；
- Open Field 密度；
- Soft Surface 形状；
- 页面主轨道 1120px、可读内容轨道 980px；
- Display Title 桌面 96px、移动端 64px 的顶部节奏；
- section gap、grid gap、圆角、阴影、导航当前态、Focus 和 reduced-motion 规则；
- 当前站点的 Header、Footer、Page Shell 和响应式 gutter。

### 2.2 已锁定的 Now 内容规则

- 内容源是 `src/site-content/now/*.md`。
- `date` frontmatter 是排序依据，格式使用 `YYYY-MM-DD`。
- 网站只显示 `date` 最新的一篇。
- 旧 Markdown 不在 Now 页面公开展示。
- 日期只用于 frontmatter 排序和最新文章判定；文章不要求日期 H1，正文可以自由写一条更新句后开始展开。
- 新增内容通过新增 Markdown 文件完成，不复制整页 HTML。

## 3. 具体工作流

### 阶段 0：明确本轮任务

确认本轮只处理 Now 文章展示 UI，不同时处理 About、Contact、Archive 或新的全局主题。

输出：

- 页面目标；
- 真实测试文章；
- 受影响路由和文件；
- 不处理的问题。

### 阶段 1：加载任务级设计知识

按照 `00-entrypoint.md`：

1. 读取 `manifest.yaml`，确认知识库版本和真源位置。
2. 从 `indexes/` 定位与页面结构、排版、响应式、组件验收相关的原则。
3. 生成本轮任务的 `context-pack.md`，只载入 Now 页面需要的原则。
4. 将规则标注为 `source`、`derived`、`project` 或 `task`。

此阶段的目的，是防止把通用经验误写成设计原则，也防止重新打开已经接受的 Foundation。

### 阶段 2：审计当前页面和真实内容

Agent 先直接检查：

- `src/pages/now.astro`；
- `src/styles/now.css` 和文章样式；
- `src/data/now.ts`、frontmatter 读取器和 Markdown 渲染器；
- 当前测试 Markdown；
- `BaseLayout`、Header、Footer 和受影响的全局样式。

检查结果要回答：

- 哪些规则已经存在，可以直接复用；
- 哪些样式只是接入用基线；
- 哪些变量确实会改变视觉判断；
- 哪些问题暂时没有真实内容依据。

### 阶段 3：冻结文章内容合同

在视觉选择前先确认文章结构：

- 文件位置和命名；
- `date` 是否必填；
- 日期格式和排序；
- 是否设置独立 H1；如果不设置，由正文承担文章开篇；
- 支持哪些 Markdown 元素；
- 图片、代码、表格、引用是否进入本轮；
- 缺少 frontmatter 或文章为空时如何处理；
- 历史版本是否只保留在本地/Git，不进入公开页面。

未被真实文章使用的复杂 Markdown 能力不提前设计成独立组件。

### 阶段 4：筛选需要单独决策的变量

把变量分为三类：

1. `LOCKED`：来自 Foundation 或已确认的站点规则，不再开放选择。
2. `P1 / MUST DECIDE`：会明显改变 Now 页面阅读体验，第一轮必须做可视化选项；如果用户已经明确拒绝 5 个视觉方案，则转为页面合同或内容合同，不继续强行选择。
3. `P2 / CONDITIONAL`：只有真实文章出现对应内容时才决策。

只有第二类变量需要制作 5 个样式选项。

### 阶段 5：制作可视化选择

不向用户展示孤立的 px、色号或 CSS 数据，而是建立一个本地 Review Preview：

- 使用同一篇真实 Markdown；
- 同时展示 A、B、C、D、E 五个方案；
- 每个方案标注改动变量；
- 保持其他变量相同，避免一次改变太多因素；
- 为每组方案保留“选择 / 不确定 / 自由反馈”位置；
- 选项只存在于 Review Preview，不直接把所有实验 CSS 带入生产。

Now Review Preview 采用极简决策界面：

- 每次只显示一个视觉要素和一篇真实文章；
- 页面只保留视觉要素名称、A–E 选择、前后切换和自由反馈；
- 删除正式网站导航、Lab 介绍、统计数字、搜索筛选、组件目录和装饰性卡片；
- 让文章预览占据主要屏幕空间，方案名称和当前状态只保留为必要标识；
- 选择和反馈保存在当前浏览器本地，不把 Review Preview 变成生产页面。

如果多个变量强相关，可以做少量组合方案，但要记录组合关系，避免无法判断原因。

### 阶段 6：记录设计决定

用户选择后记录：

- 变量 ID；
- 选择的方案；
- 选择理由；
- 放弃的方案；
- 对应的原则 ID；
- 该规则属于 `project` 还是 `task`；
- 是否需要回写 Component Contract；
- 是否影响其他页面。

如果发现规则具有跨页面价值，才提升为 Foundation 或 Component Contract 规则；否则只保留在 Now 页面合同中。

### 阶段 7：修改生产代码

Agent 根据已确认的选择直接审计和修改代码：

- 复用现有 token；
- 优先修改 Now 页面及其明确依赖；
- 不把 Lab 试验代码带入生产；
- 不为尚未出现的内容提前创建复杂组件；
- 保持 Markdown 内容与 UI 分离。

### 阶段 8：真实内容验收

至少验收：

- 桌面端 1440px；
- 约 1160px 的桌面窄视口；
- 390 × 844 移动视口；
- 日期长标题；
- 中英文、数字和标点混排；
- `h2`、`h3`、段落、无序列表、有序列表、链接、粗体、斜体、分隔线；
- 长段落和连续列表；
- 键盘 Focus；
- reduced-motion；
- 空文章、错误 frontmatter 或缺失内容的诚实状态；
- 无横向溢出；
- `npm.cmd run build`。

验收必须发生在真实渲染结果上，不能只根据源码或静态代码检查宣布完成。

### 阶段 9：回写状态

完成后更新：

- 本目录的变量决策状态；
- Component Contract（只有涉及生产合同的规则才回写）；
- Component Production Acceptance Queue 的 P1-01；
- 视觉验收记录；
- 未解决问题和下一步。

一个阶段只有在“设计决定已记录 + 真实渲染已验收 + 构建通过”后，才算完成。

## 4. 用户与 Agent 的分工

### Agent 负责

- 读取原则和项目文档；
- 审计代码、内容、CSS、数据和受影响页面；
- 生成可视化选项；
- 根据选择修改生产代码；
- 运行构建、响应式和可访问性检查；
- 回写研究文档。

### 用户负责

- 观看真实渲染结果；
- 选择方案；
- 指出“整体感觉不对”的地方；
- 对内容公开边界和文字内容做最终判断。

用户不需要阅读或理解实现代码。
